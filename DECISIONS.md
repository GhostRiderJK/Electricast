# Decisions log

One line per ambiguous choice; the more conservative option wins.

- 0.1: `data/` is deliberately **not** ignored — the 39 raw apartment CSVs are tracked project inputs and the rules forbid deleting them. `.gitignore` only covers generated artifacts and secrets.
- 0.1: `.env.example` stays un-ignored (`!.env.example`) so configuration can be documented without tracking real secrets.
- 0.2: `torch` is pinned as `2.14.1` without the local `+cpu` suffix; wheel variants are platform-specific and the plain pin resolves to the installed version on this host.
- 0.2: Docker base is the exact `python:3.12.10-slim` tag to match local Python 3.12.10. The image was not built because no Python image was cached and network use is limited to pip/npm.
- 1.1: Kept stored/displayed values in Wh and corrected labels rather than dividing every series and metric by 1000; this follows the Wh-internal rule with a smaller, auditable diff.
- 1.1: The upload CSV input column name `Energy Consumption (kWh)` is left unchanged because it is the schema of the provided dataset; its numeric values are still treated as Wh downstream (pre-existing behavior, revisited in Phase 6).
- 1.2: Model availability is expressed by a backend `status` field (`ok` / `disabled`); the stored LSTM placeholder rows remain in `model_results.json` but every metrics UI path filters on `status === "ok"`.
- 1.2: BEST ties are marked on all tied models; if no active model has a finite metric, the value renders as N/A and no badge is shown.
- 1.4: Daily means were derived from the raw CSVs with the existing 2017 cleaning pipeline and written into `model_results.json` as `eda.yearly_daily`; no model was retrained and all existing metrics/prediction arrays were verified byte-identical after the JSON update.
- 1.4: `/api/eda/yearly` returns daily means by default and falls back to the legacy sampled `eda.yearly` series if an older results file is loaded.
- 1.5: The split label shows percentages computed from `statistics.train_hours`/`test_hours` plus the raw hour counts, so the label is auditable; it renders "loading…" until statistics arrive rather than guessing.
- 1.7: R² uses a green threshold of 0.8 and red only for negative values; 0–0.8 stays neutral because no documented target exists, and coloring a merely modest score red would overstate failure.
- 1.9: The selected month/day are derived from fetched data (`selectedMonth ?? first test month`, day list from `predDaily` labels) instead of writing state during render; switching to a shorter month clamps an out-of-range day to that month's last available day.
- 1.10: The API base now defaults to same-origin (`""`); Vite dev and preview proxy `/api` to `http://localhost:8000`, and `VITE_API_URL` remains the override for split-origin deployments.
- 1.10: Muted text moved from `#9ca3af`/`#6b7280` to `#4b5563`, and small green/red accent text to `#15803d`/`#b91c1c`; chart series keep `#16a34a`/`#dc2626` because graphical elements only need 3:1.
- 1.10: Pages with several data hooks show one alert for the first failure instead of stacking duplicate banners; MetricsBar has its own alert because it renders outside page content.
- 2.3: Raw `TS` values are UTC epoch seconds, but 187,796 of 196,449 rows sit at :30 UTC (exactly on IST hours) while 8,653 rows — including all 38 May-2018 blocks — sit at :00 UTC and land at IST :30. We convert to IST and floor each stamp to its containing hour, so the :00-UTC block joins the IST hour it falls in; no apartment-hour bucket is duplicated (verified 0), and the blocks are separated by months, so no double counting.
- 2.4: The stable panel is evaluated on the longest dense block, 2017-05-01→2017-11-30 (5,136 hours): 24 of 39 apartments have ≥90% hourly coverage there (90.1–91.5%) and the other 15 are excluded. No window longer than this reaches 90% for any apartment (2017 max 79.7%, full range 58.2%).
- 2.4: `target_wh` is the mean of the reporting stable apartments in each hour and `n_reporting` counts those apartments; hours with zero stable reporters stay NaN rather than being filled. The fold windows retain 2,370 usable hours for Sep–Dec 2017 and 214 for May–Jun 2018.
- 2.5: Interior NaN runs of at most 6 h are linearly interpolated and flagged in `imputed`; longer runs and runs touching either end of the series are flagged in `excluded` and left NaN. Interpolated hours are usable for training, excluded hours are dropped from both training and evaluation (including lag/feature construction).
- 2.6: The outlier cap is Q3 + 3×IQR of the training-window target values (minimum 100 samples), clipped on the upper tail only after fitting; the fitter is always passed the training slice, never validation/test values.
- 2.7: "December" means December 2017 (the most recent December, with 38/39 apartments reporting, versus 26 in December 2016); an apartment is flagged `suspect_inactive` when its December mean is <100 Wh/h and it has at least 24 hourly readings. Flags are descriptive only — flagged apartments stay in the panel and the flag is written to data quality output.
- 2.8: `backend/data_quality.json` is generated by `backend/build_data_quality.py`, committed, and served read-only at `/api/data_quality`; it contains no absolute paths. After changing the pipeline, regenerate the JSON and restart the API because it is loaded at startup.
- 2.8: The header nav scrolls horizontally inside the header on narrow screens and hides the model badges below 760 px, so adding a sixth page does not force page-level horizontal overflow.
- 3.1: "Persistence" is the last valid observation before 00:00 IST, held constant for all 24 hours of the forecast day; the four-week baseline requires all four same-weekday lags (otherwise NaN), and lagged baselines use the gap-handled target with long gaps left missing.
- 3.2: MASE uses the mean absolute 24-h seasonal difference of the training window as its scale; WAPE/R²/MASE report null when their denominator is zero, and a zero sMAPE denominator contributes 0 instead of dropping the pair.
- 3.3: The backtest uses four expanding folds (test Jul 2017, Aug 2017, Sep–Dec 2017, May–Jun 2018) with train_start fixed at 2017-05-01; models are fit on the fold's training window only, while day-ahead forecasts may use actuals up to each day's 00:00 IST origin. Headline metrics use the hours where the target and seasonal-naive-24 forecast both exist.
- 3.4: The best baseline is chosen by lowest MASE on the all-four-baseline mask when that mask covers at least max(24 h, 50%) of the fold's evaluation hours, otherwise on the evaluation mask; ties break by MAE then name. Significance is a two-sided Wilcoxon signed-rank test on paired absolute errors with unadjusted p-values and a `small_sample` flag below 10 pairs. A model with no usable hours reports `status: no_data` and null metrics, never a zero-filled score.
- 4.1: XGBoost is one pooled direct model per fold (not recursive) using lags 24–47 h, 168 h, and 336 h, four aggregates of the 24–47 h block, and hour of day; every feature is at least 24 h old at the target hour, so it cannot read the forecast day. Training labels are clipped at the train-only cap, and predictions are clipped at zero because load cannot be negative. pytest 8.4.2 was added to `requirements.txt` solely to run the required leakage tests.
- 4.2: Reporting counts enter only as lags (same hour previous day and the 24–47 h block mean), never at the target hour. Holiday flags come from a hand-curated list of major national holidays and festivals in the data period; semester flags assume Jan–Apr and Jul–Nov in session with May–Jun and Dec breaks. Both are transparent approximations. The feature set is frozen while test metrics are inspected; any tuning happens only on train-side CV in 4.4.
- 4.3: The weather location is IIT Bombay (19.1334 N, 72.9133 E) per the dataset provenance. Open-Meteo archive responses are cached in `backend/weather_mumbai.csv` and committed; evaluation never calls the network. Weather is used only through ≥24 h lags because target-hour weather is unknown at the forecast origin. If the cache is missing, the backtest runs without weather features and records `available: false`.
- 4.4: Optuna 5.0.0 (TPE, seed 42, 30 trials) tunes each fold separately on three expanding-window CV splits entirely inside that fold's training window; no test values are read. Early stopping uses patience 25 on those train-side validation slices, and the final model uses the median best iteration across them before refitting on all training labels. Hyperparameters therefore differ by fold by design; test folds are never used to choose them.
- 4.5: SARIMA is fixed at order (1,0,1)(0,1,1,24) on the gap-handled target. It is refit on Mondays, on the first test day, and after a coverage gap, using the trailing 60 days of contiguous history ending one hour before the origin; within a week the fitted state is advanced with actuals strictly before each origin. A refit requires at least 7 contiguous days, and a forecast is skipped when the newest state is more than 48 h old, because a five-month-stale state produced unusable 2018 predictions. Negative forecasts are clipped to zero.
- 4.5: SARIMA is scored only on hours where it emits a forecast; coverage is recorded in `model_fit.sarima.predicted_hours` and `models.sarima.n`, and paired significance uses the overlapping hours. This matches the existing treatment of lagged baselines that also have partial coverage; the evaluation mask itself is unchanged.
- 4.6: The quantile model fits three independent XGBoost regressors with `objective=reg:quantileerror` at alphas 0.1, 0.5, and 0.9 on the same features, lags, training window, and train-only cap as the point XGBoost, using the fixed untuned 4.1 defaults. Predictions are clipped at zero and sorted row-wise to enforce P10 ≤ P50 ≤ P90; the crossing count is recorded. Interval quality is judged by P10–P90 coverage, mean width, and pinball loss, with P50 additionally scored as a point forecast. No test-window calibration or tuning is applied; the autumn undercoverage is reported as a limitation.
- 4.7: No validated LSTM/GRU is shipped, so the second branch of the item is taken: the model is omitted from the UI entirely rather than shown as a placeholder. Its metrics cards, page entries, prediction toggles, chart datasets, color/meta entries, and EDA copy were removed. The backend keeps the disabled legacy keys in `/api/metrics` and prediction payloads for schema compatibility, but no UI path selects or renders them; README and copilot docs are corrected in 7.3.
- 5.1: The metrics page and bar read `/api/backtest/summary`, derived at backend startup from `results.json`; fold means are unweighted across folds with sample std, and "beats seasonal naive" is a descriptive majority over folds where both models have data, not a replacement for the per-fold paired Wilcoxon results.
- 5.1: All seven models are shown in the metrics table, but the top metrics bar keeps only learned models so the header does not repeat baselines; numbers remain backend-sourced in both places.
- 5.2: Hourly backtest rows are persisted in `results.json` on the existing evaluation mask rather than recomputed per request, and day/error aggregates are derived from that artifact at backend startup; models with partial coverage contribute only their available hours (their n is reported).
- 5.2: "Worst days" ranks by XGBoost MAE with a 12-evaluable-hour minimum so one transparent criterion is used and very short days cannot dominate; per-model MAEs and n are shown for context.
- 5.2: The Predictions page now uses only the four-fold backtest data; the earlier single-split `/api/predictions/*` charts were removed from that page (the endpoints remain for other consumers and schema compatibility).
- 5.3: Gain importance (XGBoost booster `get_score(importance_type="gain")`, normalized to shares) is used instead of SHAP to avoid a new dependency and any retraining; it is computed inside each fold's training window and is descriptive, not causal. Lags sharing credit is stated on the page.
- 5.3: Residuals are actual − forecast from the persisted hourly backtest rows, and each model is summarized only on hours where its own forecast exists; no test-window refitting, calibration, or imputation is performed for display.
- 5.4: Limitations are a dedicated page backed by `/api/limitations`, which aggregates `data_quality.json` and `results.json` rather than duplicating numbers in JSX. The page labels items high / medium / context; the long target gap, thin 2018 fold, partial SARIMA coverage, interval undercoverage, and suspect inactivity are high because they most affect how a headline number should be read.
- 5.4: The panel reports scope limits as descriptive caveats only and does not attempt to correct or recalibrate them. The stale LSTM mention was removed from the FastAPI description, but legacy backend response keys stay until 7.3/documentation cleanup.
- 6.1: Upload units are declared by the user: Wh/kWh readings are energy and are summed within each series-hour, while W/kW readings are average power and are averaged within each series-hour; kWh and kW are then multiplied by 1,000 to Wh. The target is the unweighted mean across reporting series, matching the campus `target_wh` definition. Negative readings are excluded as invalid load.
- 6.1: Timestamp handling supports epoch seconds/milliseconds, date strings with embedded offsets, and naive date strings localized with the selected zone. Everything is converted to IST before hourly flooring; the selected timezone is ignored when the timestamp is absolute, and the report states which rule was used.
- 6.2: The upload evaluation reuses the Phase 3 baselines, evaluation mask, MASE scale, best-baseline selection, and paired Wilcoxon test. The 60/40 split is chronological at the first IST day boundary after the 60th-percentile valid hour, so test days always have a 00:00 origin and no test-window label enters training.
- 6.2: The zero-shot model is retrained on the campus target with only features available for a new upload (>=24 h target lags and calendar); campus reporting counts and weather are excluded so training and inference share a feature set. Its scale factor uses only the training-part mean, never the test part. The fit-on-60% model uses the fixed 4.1 defaults and a train-only cap, with no tuning on uploaded data.
- 6.2: Short or gappy uploads return a partial validation report with an explicit reason instead of metrics; degenerate series can leave the best baseline or significance empty, and the UI shows N/A. No placeholder or fitted-on-test score is displayed.
- 6.3: The full file is streamed once with a hard 50 MB limit; the preview sends only the first 256 KB. 6.1, 6.2, and 6.3 share the same module/endpoints/page and are committed together, with per-item evidence recorded in PROGRESS.md.
- 6.3: No new frontend or backend dependencies were added for the upload redesign; progress uses XMLHttpRequest because fetch has no upload-progress event in browsers.
- 7.2: The backend image now copies the complete runtime directory (excluding tests and caches), so `upload_validation.py`, the pipeline/evaluation modules, weather cache, JSON artifacts, and `models/` are present; the campus CSV directory is mounted read-only at `/data` because the zero-shot upload model reads it on first use. The healthcheck uses the Python standard library because `python:3.12-slim` has no curl, and the frontend relies on nginx's same-origin `/api/` proxy instead of a runtime `VITE_API_URL` that Vite cannot read after build.
- 7.2: `torch==2.14.1` was removed from `requirements.txt`: the only import is inside the commented-out legacy LSTM block, and the CUDA-enabled wheel stack added roughly 6.6 GB to the backend install without any runtime user. Re-enabling that LSTM requires reinstalling torch first.
- 7.2: Linux installs `xgboost-cpu==3.4.1` instead of `xgboost==3.4.1`; the regular Linux wheel hard-depends on `nvidia-nccl-cu13` (305 MB) even though this service only trains and predicts on CPU. Windows keeps the regular wheel via an environment marker, and both packages expose the same `xgboost` 3.4.1 API.
- 7.3: Documentation treats `results.json` + `data_quality.json` as the current evaluation product and `model_results.json` as the legacy 2017 single-split aggregate; the EDA and Weekly pages keep their legacy endpoints, and README/copilot docs warn that the two products are not directly comparable, rather than changing UI behavior in a docs-only item.
- 8.1: The assistant defaults to the locally installed Ollama `llama3.2:3b` because it is a small, already-available CPU model; Gemini (`gemini-2.5-flash`) is an optional fallback only when `GEMINI_API_KEY` is set. HTTP uses the Python standard library, so no new dependency was added. The network scope was widened by this item's explicit request to local Ollama and (if configured) Gemini; nothing else was added.
- 8.1: Tool selection is a deterministic keyword/date/month/hour router in `chat_tools.plan()` rather than model-initiated tool calls. A 3B local model chose tools unreliably in design review, while a deterministic router makes the sample questions reproducible and keeps unsupported questions from reaching the provider at all.
- 8.1: The grounding guard checks every digit token, ISO date, fold id, and clock time in the answer against the tool-result packet. Values equal to a packet value or a rounded version of one are accepted; ordered-list markers are ignored. A rejected answer is retried once with the rejected tokens, then HTTP 502. The guard enforces numeric provenance, not semantic truth: it does not verify that a grounded number is used in the correct context, and it does not catch a number spelled out in words (the prompt forbids both). The December tool output now carries a deterministic summary to prevent a load threshold being misread as a weather threshold.
- 8.1: `GET /api/chat/status` returns HTTP 200 with `available:false` whenever no provider is reachable, so the dashboard never depends on the assistant. The drawer hides the composer in that state and offers a recheck; an unreachable API or a 502/503 during a question is shown as a visible error with retry. Single-turn only (no message history is sent), artifacts only, 500-character questions, 60 s provider timeout.
- 8.1: The Gemini path was implemented against the REST API and covered by mocked pytest cases but has not been exercised live because this host has no API key. Docker Compose defaults `OLLAMA_URL` to `http://host.docker.internal:11434` with an `extra_hosts` mapping; the host Ollama must listen on `0.0.0.0` (not only loopback) for a container to reach it.
- 9.1: Every fold's `train_start` is now derived at runtime as the first valid target hour (`evaluate.history_start`) instead of a hardcoded date. The current value is 2016-12-14 21:00 IST. This keeps the "use all valid history" invariant true if the target or gap handling changes, and each fold still grows only forward to its own `train_end`.
- 9.1: `backend/results_v1.json` is a byte copy of the pre-9.1 `results.json` (generated 2026-10-23T19:30:48+05:30) and is kept for before/after comparison. `results.json` remains the only artifact the API, UI, and assistant read; `results_v1.json` is never loaded at runtime.
- 9.1: The December 2016 comparison uses the same descriptive rule as December 2017 (mean <100 Wh/h over at least 24 readings). The premise that Dec 2016 shows the same vacancy pattern is not supported: 7 apartments were flagged in Dec 2016 (7 of 26 with readings) versus 21 in Dec 2017 (21 of 38), and only 6 flagged apartments are shared (Jaccard 0.27). The two Decembers are therefore treated as separate context, not as one recurring pattern.
- 9.2: The 2018 fold keeps its id `2018-05_06` so existing day/fold URLs and records stay valid, but carries `stress_test: true` and the label "Stress test (May–Jun 2018)". The API summary, assistant tools, and UI compute fold means, standard deviations, coverage and "beats" counts from the five scoring folds only; the stress test is still shown as a per-fold column for context.
- 9.2: December 2017 is now its own scoring fold (548 evaluable hours) rather than being pooled into Sep–Dec. This makes the vacancy regime visible instead of hidden in an aggregate: every learned model loses badly to persistence there, and the API says so per fold. June 2017 is also its own fold, trained from Dec 2016 through May 2017.
- 9.2: JSON artifacts are read with explicit UTF-8 in `main.py`. Python's default open() uses the Windows locale codec, which turned the stress label's en dash into mojibake in the API and UI; the artifact itself was already written as UTF-8.
- 9.3: The feature ablation holds the model configuration fixed at untuned `forecast_model.DEFAULT_PARAMS` across every variant and fold. Re-tuning each feature set separately would mix feature effects with tuning noise and would preview 9.5; the tuned production numbers stay in `results.json`. All variants share the same folds, evaluation mask (target + seasonal naive), train-only cap, and reporting-count features.
- 9.3: "Drop annual calendar" removes only `month`, `doy_sin`, and `doy_cos`; hour of day, day of week, weekend, holiday, and semester flags remain. It applies only when the training span is shorter than 365 days, which is true for all five scoring folds (351 days at most) and false for the 2018 stress test (382 days). In the stress fold the variant is recorded as `applied:false` and is identical to the full model, so it never contributes a fake win.
- 9.3: `no_annual_calendar` is kept: it helped 4 of 5 scoring folds (Jun −0.53, Aug −0.49, Sep–Nov −0.07, Dec −31.28 Wh; July +0.21) with mean MAE 107.66 vs 114.09 Wh for full features. The decision is driven by December; three of the four wins are under 0.6 Wh, and that is stated rather than treated as a broad effect. 9.4 compares against this feature configuration.
- 9.3: `no_weather` is discarded (helped only Sep–Nov −1.77 and Dec −12.56; worse in Jun, Jul, Aug; mean −2.32). The ORACLE same-hour temperature variant helped 3 of 5 folds but reads temperature at the target hour, which is unknown at the 00:00 IST origin. It is flagged `oracle:true` and `diagnostic_only:true` in `ablation_results.json`, is excluded from the kept set and the winner, and is never written to `results.json` or presented as a real result. The keep rule is strict MAE improvement on a scoring fold; the 2018 stress test is reported for context only.
