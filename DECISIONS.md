# Decisions log

One line per ambiguous choice; the more conservative option wins.

- 0.1: `data/` is deliberately **not** ignored — the 39 raw apartment CSVs are tracked project inputs and the rules forbid deleting them. `.gitignore` only covers generated artifacts and secrets.
- 0.1: `.env.example` stays un-ignored (`!.env.example`) so configuration can be documented without tracking real secrets.
- 0.2: `torch` is pinned as `2.14.1` without the local `+cpu` suffix; wheel variants are platform-specific and the plain pin resolves to the installed version on this host.
- 0.2: Docker base is the exact `python:3.12.10-slim` tag to match local Python 3.12.10. The image was not built because no Python image was cached and network use is limited to pip/npm.
- 1.1: Kept stored/displayed values in Wh and corrected labels rather than dividing every series and metric by 1000; this follows the Wh-internal rule with a smaller, auditable diff.
- 1.1: The upload CSV input column name `Energy Consumption (kWh)` is left unchanged because it is the schema of the provided dataset; its numeric values are still treated as Wh downstream (pre-existing behavior, revisited in Phase 6).
- 1.2: Model availability is expressed by a backend `status` field (`ok` / `disabled`); the stored LSTM placeholder rows remain in `model_results.json` but every metrics UI path filters on `status === "ok"`.
- 1.2: BEST ties are marked on all tied models; if no active model has a finite metric, the value renders as N/A and no badge is shown.
- 1.4: Daily means were derived from the raw CSVs with the existing 2017 cleaning pipeline and written into `model_results.json` as `eda.yearly_daily`; no model was retrained and all existing metrics/prediction arrays were verified byte-identical after the JSON update.
- 1.4: `/api/eda/yearly` returns daily means by default and falls back to the legacy sampled `eda.yearly` series if an older results file is loaded.
- 1.5: The split label shows percentages computed from `statistics.train_hours`/`test_hours` plus the raw hour counts, so the label is auditable; it renders "loading…" until statistics arrive rather than guessing.
- 1.7: R² uses a green threshold of 0.8 and red only for negative values; 0–0.8 stays neutral because no documented target exists, and coloring a merely modest score red would overstate failure.
- 1.9: The selected month/day are derived from fetched data (`selectedMonth ?? first test month`, day list from `predDaily` labels) instead of writing state during render; switching to a shorter month clamps an out-of-range day to that month's last available day.
- 1.10: The API base now defaults to same-origin (`""`); Vite dev and preview proxy `/api` to `http://localhost:8000`, and `VITE_API_URL` remains the override for split-origin deployments.
- 1.10: Muted text moved from `#9ca3af`/`#6b7280` to `#4b5563`, and small green/red accent text to `#15803d`/`#b91c1c`; chart series keep `#16a34a`/`#dc2626` because graphical elements only need 3:1.
- 1.10: Pages with several data hooks show one alert for the first failure instead of stacking duplicate banners; MetricsBar has its own alert because it renders outside page content.
- 2.3: Raw `TS` values are UTC epoch seconds, but 187,796 of 196,449 rows sit at :30 UTC (exactly on IST hours) while 8,653 rows — including all 38 May-2018 blocks — sit at :00 UTC and land at IST :30. We convert to IST and floor each stamp to its containing hour, so the :00-UTC block joins the IST hour it falls in; no apartment-hour bucket is duplicated (verified 0), and the blocks are separated by months, so no double counting.
- 2.4: The stable panel is evaluated on the longest dense block, 2017-05-01→2017-11-30 (5,136 hours): 24 of 39 apartments have ≥90% hourly coverage there (90.1–91.5%) and the other 15 are excluded. No window longer than this reaches 90% for any apartment (2017 max 79.7%, full range 58.2%).
- 2.4: `target_wh` is the mean of the reporting stable apartments in each hour and `n_reporting` counts those apartments; hours with zero stable reporters stay NaN rather than being filled. The fold windows retain 2,370 usable hours for Sep–Dec 2017 and 214 for May–Jun 2018.
- 2.5: Interior NaN runs of at most 6 h are linearly interpolated and flagged in `imputed`; longer runs and runs touching either end of the series are flagged in `excluded` and left NaN. Interpolated hours are usable for training, excluded hours are dropped from both training and evaluation (including lag/feature construction).
- 2.6: The outlier cap is Q3 + 3×IQR of the training-window target values (minimum 100 samples), clipped on the upper tail only after fitting; the fitter is always passed the training slice, never validation/test values.
- 2.7: "December" means December 2017 (the most recent December, with 38/39 apartments reporting, versus 26 in December 2016); an apartment is flagged `suspect_inactive` when its December mean is <100 Wh/h and it has at least 24 hourly readings. Flags are descriptive only — flagged apartments stay in the panel and the flag is written to data quality output.
- 2.8: `backend/data_quality.json` is generated by `backend/build_data_quality.py`, committed, and served read-only at `/api/data_quality`; it contains no absolute paths. After changing the pipeline, regenerate the JSON and restart the API because it is loaded at startup.
- 2.8: The header nav scrolls horizontally inside the header on narrow screens and hides the model badges below 760 px, so adding a sixth page does not force page-level horizontal overflow.
- 3.1: "Persistence" is the last valid observation before 00:00 IST, held constant for all 24 hours of the forecast day; the four-week baseline requires all four same-weekday lags (otherwise NaN), and lagged baselines use the gap-handled target with long gaps left missing.
- 3.2: MASE uses the mean absolute 24-h seasonal difference of the training window as its scale; WAPE/R²/MASE report null when their denominator is zero, and a zero sMAPE denominator contributes 0 instead of dropping the pair.
- 3.3: The backtest uses four expanding folds (test Jul 2017, Aug 2017, Sep–Dec 2017, May–Jun 2018) with train_start fixed at 2017-05-01; models are fit on the fold's training window only, while day-ahead forecasts may use actuals up to each day's 00:00 IST origin. Headline metrics use the hours where the target and seasonal-naive-24 forecast both exist.
- 3.4: The best baseline is chosen by lowest MASE on the all-four-baseline mask when that mask covers at least max(24 h, 50%) of the fold's evaluation hours, otherwise on the evaluation mask; ties break by MAE then name. Significance is a two-sided Wilcoxon signed-rank test on paired absolute errors with unadjusted p-values and a `small_sample` flag below 10 pairs. A model with no usable hours reports `status: no_data` and null metrics, never a zero-filled score.
- 4.1: XGBoost is one pooled direct model per fold (not recursive) using lags 24–47 h, 168 h, and 336 h, four aggregates of the 24–47 h block, and hour of day; every feature is at least 24 h old at the target hour, so it cannot read the forecast day. Training labels are clipped at the train-only cap, and predictions are clipped at zero because load cannot be negative. pytest 8.4.2 was added to `requirements.txt` solely to run the required leakage tests.
- 4.2: Reporting counts enter only as lags (same hour previous day and the 24–47 h block mean), never at the target hour. Holiday flags come from a hand-curated list of major national holidays and festivals in the data period; semester flags assume Jan–Apr and Jul–Nov in session with May–Jun and Dec breaks. Both are transparent approximations. The feature set is frozen while test metrics are inspected; any tuning happens only on train-side CV in 4.4.
- 4.3: The weather location is IIT Bombay (19.1334 N, 72.9133 E) per the dataset provenance. Open-Meteo archive responses are cached in `backend/weather_mumbai.csv` and committed; evaluation never calls the network. Weather is used only through ≥24 h lags because target-hour weather is unknown at the forecast origin. If the cache is missing, the backtest runs without weather features and records `available: false`.
- 4.4: Optuna 5.0.0 (TPE, seed 42, 30 trials) tunes each fold separately on three expanding-window CV splits entirely inside that fold's training window; no test values are read. Early stopping uses patience 25 on those train-side validation slices, and the final model uses the median best iteration across them before refitting on all training labels. Hyperparameters therefore differ by fold by design; test folds are never used to choose them.
- 4.5: SARIMA is fixed at order (1,0,1)(0,1,1,24) on the gap-handled target. It is refit on Mondays, on the first test day, and after a coverage gap, using the trailing 60 days of contiguous history ending one hour before the origin; within a week the fitted state is advanced with actuals strictly before each origin. A refit requires at least 7 contiguous days, and a forecast is skipped when the newest state is more than 48 h old, because a five-month-stale state produced unusable 2018 predictions. Negative forecasts are clipped to zero.
- 4.5: SARIMA is scored only on hours where it emits a forecast; coverage is recorded in `model_fit.sarima.predicted_hours` and `models.sarima.n`, and paired significance uses the overlapping hours. This matches the existing treatment of lagged baselines that also have partial coverage; the evaluation mask itself is unchanged.
- 4.6: The quantile model fits three independent XGBoost regressors with `objective=reg:quantileerror` at alphas 0.1, 0.5, and 0.9 on the same features, lags, training window, and train-only cap as the point XGBoost, using the fixed untuned 4.1 defaults. Predictions are clipped at zero and sorted row-wise to enforce P10 ≤ P50 ≤ P90; the crossing count is recorded. Interval quality is judged by P10–P90 coverage, mean width, and pinball loss, with P50 additionally scored as a point forecast. No test-window calibration or tuning is applied; the autumn undercoverage is reported as a limitation.
- 4.7: No validated LSTM/GRU is shipped, so the second branch of the item is taken: the model is omitted from the UI entirely rather than shown as a placeholder. Its metrics cards, page entries, prediction toggles, chart datasets, color/meta entries, and EDA copy were removed. The backend keeps the disabled legacy keys in `/api/metrics` and prediction payloads for schema compatibility, but no UI path selects or renders them; README and copilot docs are corrected in 7.3.
